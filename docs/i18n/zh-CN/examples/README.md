# 验证实例

> 规范的权威来源是英文文档。如果译文与已测试的约定存在冲突，以已测试的英文约定为准。

这些页面完整呈现了 Xerify 的工作方式：一个有边界的主张、可能离开本机的证据、唯一明确指定的目标模型、归一化后的结果，以及调用方应做出的退出决策。

这些都是**真实运行的记录**，不是预设好的裁定。页面上的每个结果，都是在标注的日期、执行标注的命令得到的。重新运行是一次新的验证，不是对原结果的重放保证——[失败模式](failure-modes.md)记录了一个真实案例：同一条命令跑出了两种不同的结果。

## 没有提供方账号？从这里开始

[零账号演练](no-account-walkthrough.md)使用包内自带的确定性模拟提供方，在不消耗任何提供方配额的情况下，复现**每一种裁定和每一种类型化失败**。在真正花掉一次调用之前，这是理解退出码约定最快的方式。

## 失败目录

[失败模式](failure-modes.md)记录了每一种非 `confirmed` 的结果：触发原因、准确输出、背后的道理，以及怎么改才能拿到可用的结果。内容涵盖提供方 CLI 未安装、CLI **未登录**、双方使用同一提供方被拒、Cursor 的 `auto` 模型、用散文代替 JSON 作答、截断或不符合模式的响应、提供方进程非零退出、超时、输出截断，以及实测中出现的运行间波动。

接入之前先读一遍。最常见的接入错误，是把退出码 `11` 当成一种情况处理，而它实际上是两种——一种是真正的 `unclear` 裁定，另一种只是套着相同裁定字符串外壳的操作性失败。

## 验证到底是什么感觉

[Dogfood](dogfooding.md) 记录了这样一件事：为了核验关于 Xerify 自身的五项发现，在 `codex` 和 `cursor` 两条通道上一共跑了 26 轮 `xerify verify`。9 轮拿到了 `confirmed`，2 轮因为主张本身是错的而拿到 `refuted`，12 轮因为证据没能证明主张所说的内容而拿到 `unclear`。它列出了全部四类被拒绝的原因，逐字引用了每一次异议，并展示了最终通过时证据包的样子。

在你写下第一条主张之前，先读一遍这页。它决定了你是花两轮，还是花十一轮。

## 真实示例

五个业务场景全部是虚构的，不包含任何真实参与者、客户、分析或项目数据。两个 Dogfood 场景使用的是 Xerify 公开发布的包和源码证据。主张的来源信息由 CLI 自行声明，Xerify 并不会假装这种声明等同于远程认证。

| 示例                                                                          | 目标调用提供方 / 模型                | 结果        | 退出码 |
| ----------------------------------------------------------------------------- | ------------------------------------ | ----------- | -----: |
| [研究论文](research-paper.md) — 所主张的结果从未被测量过                      | Anthropic / `claude-fable-5`         | `unclear`   |     11 |
| [游戏制作计划](game-design.md) — 产能计算对不上                               | Cursor / `cursor-grok-4.6-high-fast` | `refuted`   |     10 |
| [网站决策](website-decision.md) — 决策矩阵选出的是另一个方案                  | Anthropic / `claude-fable-5`         | `refuted`   |     10 |
| [数据分析](data-analysis.md) — 一个在分层后结论逆转的汇总指标                 | Cursor / `cursor-grok-4.6-high-fast` | `refuted`   |     10 |
| [外发数据审查](outbound-data-policy.md) — 假名化不等于获得授权                | Anthropic / `claude-fable-5`         | `refuted`   |     10 |
| [Dogfood：Cursor 适配器](dogfood-cursor-adapter.md) — Xerify 检查自己的源码   | OpenAI / `gpt-5.6-sol`               | `confirmed` |      0 |
| [Dogfood：npm 包边界](dogfood-package-boundary.md) — 已发布的包里到底装了什么 | Anthropic / `claude-fable-5`         | `confirmed` |      0 |

七个里有五个没有通过。这个比例正是意义所在：一个大多数时候都表示同意的验证方，并没有提供多少信息量。

## 如何读懂一个示例

每个页面都分成六个部分：

1. **主张** — 待证伪的命题，不是求认同的请求。
2. **复现步骤** — 完整命令，照原样即可运行。
3. **证据** — 发送给目标提供方的唯一有边界的材料。
4. **观察到的归一化结果** — 经过 Xerify 严格解析器处理后挑选出的字段，绝不是提供方的原始输出。
5. **裁定依据** — 验证方究竟攻击了主张的哪个部分，换成较弱的检查会漏掉什么。
6. **改变结果的关键** — 能让结果朝任一方向变化的具体证据。

复现命令会消耗配额。先看一遍证据文件，再把模型 ID 换成你账号下实际可用的那个。

## 机器可读目录

[index.jsonl](../../../examples/index.jsonl) 为每个验证示例保存一条紧凑的归一化记录，每行一个 JSON 对象。智能体可以先搜索这份索引，再决定要不要打开对应的 Markdown 页面。

它刻意排除了提供方原始传输数据、结果 ID、耗时、账号与会话信息，以及成本/用量字段。

```sh
# 所有未通过的示例
grep -v '"exitCode":0' docs/examples/index.jsonl

# 所有与外发数据相关的内容
grep -i 'outbound' docs/examples/index.jsonl
```

## 证据文件

[evidence/](../../../examples/evidence/) 保存的是每次验证实际收到的有边界材料，逐字不差。这些文件是**哈希锚定的验证工件**：本地运行历史会在调用时记录证据的 SHA-256 值，一旦改动文件，记录与文档之间的对应关系就会失效。

正因如此，证据文件**只保留英文，不做翻译**。本目录下的说明性页面会本地化，但它们引用的证据本身不会。

## 这些示例不代表什么

- 不是证明。`confirmed` 裁定只说明在提供的证据里没有找到反例。
- 不保证逐字复现。模型会持续更新，这里有两次运行都是第二次尝试才成功的。
- 不代表对任何模型的背书。提供方的名字从来不是质量保证——参见 Cursor 适配器 Dogfood 中连续两次退出码 `6` 的结果。
