# 安全政策

> 规范的权威来源是英文文档。如果译文与已测试的约定存在冲突，以已测试的英文约定为准。

## 报告

如果怀疑存在安全漏洞，或者不小心泄露了凭据，请不要开公开 issue，改用
[GitHub 私密漏洞报告](https://github.com/VerhexIO/xerify/security/advisories/new)。
请附上受影响的版本、影响范围、复现步骤，以及你能想到的缓解方案；不要附上真实凭据或敏感的生产环境数据。

在第一个签名发布版本之前，没有任何版本处于公开支持状态。正式发布之后，最新的次版本发布线会持续获得安全修复；支持情况表会更新在这里。

## 安全模型

Xerify 把传入的证据和提供方的输出都当作不受信任的数据来处理。验证用的 prompt 会明确把主张/context 归类为证据而不是指令，并要求以对抗性的方式去尝试证伪。这能降低“指令混淆”的风险，但不能让 LLM 完全免疫 prompt 注入。Xerify 永远不会执行模型输出，也永远不会把某个已配置的字符串当作 shell 命令去求值。Process 适配器以 `shell: false` 的方式启动一个可执行文件和参数数组，转发一份白名单化的环境变量，把 prompt/context 通过 stdin 发送，对 stdout/stderr 设置边界，并在超时或取消时终止整棵进程树。

实际生效的指令优先级依次是：Xerify 的验证约定、当前选定的操作、所有者认可的
证据范围，最后才是不受信任的主张/context。出现在代码、diff、日志、
注释、文档，或者之前模型输出里的文字，都无权合法地改变任务本身、裁定规则，或
响应模式。模型仍然可能处理不好这条边界，所以核心的模式校验和失败即拒绝（fail-closed）的结果，依然是强制性的。

官方 CLI 适配器不会在用户的仓库里运行。Codex 使用一个临时的只读
沙箱，忽略用户的配置/规则。Claude 使用一个全新的、权限模式为 `0700` 的临时目录，开启安全
模式，不带工具，不带斜杠命令，也不做会话持久化。Cursor 使用一个全新的、权限模式为 `0700` 的
工作区、只读的 ask 模式，外加它自己的沙箱。Cursor Agent 目前没有提供一个能彻底
禁用账号级全部 MCP server 的开关；这是一项已知的残留边界，而不是一个被隐藏的保证。直连 API 的适配器没有本地文件系统/工具访问权限。通用的
command 适配器是所有者显式配置的代码，默认在一个全新的临时目录里运行，但依然
继承那个可执行文件本身及其允许环境的安全性。

直连 API 的密钥，应当从具名的环境变量读取。对于基础的单用户场景，直连
HTTP 适配器也接受一个显式配置的明文 `apiKey` 作为兜底；两者都存在时，以环境变量为准。提供方的
endpoint URL 同样敏感，因为凭据可能被嵌在 userinfo、路径、查询参数或 fragment 里。
配置文件默认被 git 忽略；在 POSIX 系统上，除非权限模式是 `0600`，否则明文 key 或显式
endpoint 配置会被拒绝；查看配置时，明文 key 和完整的 endpoint 值都会被替换成
`[REDACTED]`。Windows 用户必须设置仅所有者可访问的 ACL。应当优先使用具名的 key 环境变量。带有 userinfo、
查询参数或 fragment 的兼容 endpoint——以及任何没有显式声明 key
的远程 endpoint——身份认证状态会被报告为未知，而不是被当作“不需要认证”。官方 CLI 的
凭据存储只通过官方 CLI 使用。可选的 JSONL 审计日志不包含 prompt、context、答案、findings、
提供方的原始负载、authorization 数据，以及凭据路径。新建的 POSIX 日志文件使用权限模式 `0600` 和 `O_NOFOLLOW`；每个平台都会拒绝打开非常规文件。Windows 不提供同等的原子级“不追踪符号链接”保证，因此审计日志应放在一个仅所有者可控的目录里。

项目状态存放在 `.xerify/` 下；一套受保护的直接安装生命周期，或者
`xerify init` 命令，会创建 `.xerify/xverify-config.json`、私有的日志/运行/归档目录，以及项目根目录
`.gitignore`、`.npmignore`、`.dockerignore` 里的忽略保护。这些保护属于纵深防御，
而不是访问控制：手动把文件强行加入 Git、npm，或者容器构建上下文，依然可能泄露它们。

运行历史被有意设计得比对敏感信息安全的审计日志更详细。在默认的
`captureInput: "full"` 下，主张、question 和提供的 context，都会被存储在本地的 `.xerify/runs` 里；
规范化后的结果，也可能包含提供方撰写的 findings。原始的传输响应、认证数据，以及环境快照，永远不会被写入。对于敏感项目，请使用
`metadata` 或 `none` 捕获模式，限制文件系统访问权限，并制定一套保留/删除策略。`runs show` 要求先加上
`--include-evidence`，才会打印证据内容。每次运行还带有一个有边界的、用于发现的
`head`：full 捕获模式下是一段简短的主张/question 预览，metadata 捕获模式下只有一个
摘要，none 捕获模式下不含任何来自输入的内容。归档的运行可以通过
`.xerify/archive/index.jsonl` 找到；这份索引只包含有边界的 head 和运行元数据，绝不包含
context、答案、findings、证据正文，或提供方的原始输出。它的记录摘要有助于定位
和比对某个快照，但这份索引并不是一本能对抗“同用户进程”篡改的防篡改账本。在打开匹配到的完整记录之前，应优先使用 `xerify runs search` 或直接查这份索引。
整个生命周期不会覆盖已有数据，不会发起网络/提供方调用，并且会跳过全局、
嵌套传递、`--no-save`，以及 `npx` 安装。npm 首次安装时直接依赖/传递依赖的提升顺序存在
歧义，这一点已经记录在案；嵌入方可以设置 `XERIFY_SKIP_AUTO_INIT=1`。不要强行把项目状态加入版本控制，也不要削弱自动生成的忽略规则。

Streamable HTTP 默认只走回环地址，会校验 Host 和 Origin，非回环绑定则需要显式确认，外加 bearer 身份认证。TLS、密钥轮换、网络策略、限流、多用户授权，以及日志采集的安全性，仍然由运维方负责。

## 局限性

`confirmed` 这个裁定的含义是：验证方在给定证据下没有找到实质性的反例，并且已经报告了局限性；它不是安全保证，不是形式化验证，也不是执行某项变更的许可。跨提供方复核仍然可能共享模型血统、训练数据、盲区，或者被污染的 context。证据引用是模型自己报告的指针，不是经过核实的引用来源。请把敏感输入控制在最小范围内，并独立复核所有 findings。

提供方的隔离判定，基于调用/计费/控制服务本身。即使目录 ID 里写的是 GPT、Claude 或 Gemini，只要是经由 Cursor 调用的模型，一律记为 `cursor`。因此，直连厂商的调用和经由 Cursor 的调用，可以同时满足“提供方不同”的检查，但底层用的仍可能是相关甚至完全相同的上游模型血统。请把渠道多样性当作纵深防御的一部分，而不要当作模型相互独立的证明。

单靠 prompt 层面的手段，无法彻底防住注入攻击。在发起真实调用之前，请仔细检查那份有边界的
stdin 范围：排除凭据、环境变量转储、客户数据、无关的源代码，以及认证存储。优先传入
生成好的 diff/测试输出，而不是整个仓库。让提供方的 CLI、扩展、插件、MCP 配置，以及账号策略都保持可信、保持更新。把
`unclear`、截断、结构化输出无效、超时，或适配器失败都当作非成功状态，在依据任何裁定采取行动之前，都要求做独立的测试验证。
